# Question 4: Real-Time Log Monitoring Pipeline

## Design Overview

The `monitor_log.sh` script continuously monitors a log file as it grows and filters only the lines containing **ERROR** messages. These error messages are displayed instantly on the terminal while also being saved to a separate report file for future reference. Any unnecessary error output generated by the monitoring commands is suppressed to keep the display clean.

---

## Commands Executed and Their Purpose

### `chmod +x monitor_log.sh`

### `touch system.log`

Made the monitoring script executable and created the log file if it did not already exist. This prevents `tail` from reporting a "file not found" error when monitoring begins.

### `./monitor_log.sh`

*(Started in the background during testing; in normal use it runs in a separate terminal.)*

Executed the monitoring script. It remained active, continuously watching `system.log` and displaying only the lines containing **ERROR** as new log entries were added.

### Simulating Log Activity

```bash
echo "$(date) INFO: Server started" >> system.log
echo "$(date) ERROR: Disk space low" >> system.log
echo "$(date) ERROR: Connection timeout" >> system.log
echo "$(date) INFO: Request handled" >> system.log
echo "$(date) ERROR: Database connection failed" >> system.log
```

These commands simulated an application writing log messages to the file.

As new entries were appended:

* The **INFO** messages were ignored.
* The three **ERROR** messages were detected immediately and displayed by the monitoring script.
* The near-instant response confirmed that the pipeline was processing data in real time rather than waiting until the file was complete.

### `cat error_report.txt`

Displayed the contents of the generated report file.

The file contained all three **ERROR** messages, confirming that the script not only displayed them live but also stored them permanently for later analysis.

## Explanation of the Pipeline

### `tail -f`

`tail -f` continuously watches the log file for newly appended lines instead of reading it once and exiting. This enables live monitoring of applications that are actively generating log entries.

### Pipe (`|`)

The pipe operator transfers the output from one command directly to the next without creating temporary files. This allows the log data to be filtered immediately while keeping memory and disk usage low.

### `grep --line-buffered "ERROR"`

`grep` selects only the lines containing the keyword **ERROR**.

The `--line-buffered` option forces `grep` to output each matching line as soon as it is received, preventing delays that can occur with normal buffering during long-running pipelines.

### `tee -a`

`tee` duplicates the filtered output stream.

One copy is displayed on the terminal so the user can monitor errors live, while the other copy is appended to `error_report.txt`, creating a permanent record without requiring an additional command.

### `2>/dev/null`

This redirection discards standard error messages generated by `tail`, such as temporary warnings caused by log rotation or brief file access issues. Suppressing these messages keeps the monitoring output focused only on relevant log entries.

Overall, the pipeline follows the Unix philosophy by combining several small utilities, each responsible for a single task:

* `tail` handles continuous log monitoring.
* `grep` filters the required messages.
* `tee` sends the output to multiple destinations.
* `/dev/null` suppresses unwanted error output.

This approach is lightweight, efficient, and well suited for real-time log analysis.
